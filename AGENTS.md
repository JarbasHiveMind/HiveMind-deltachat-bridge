# AGENTS.md — `HiveMind-deltachat-bridge`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

Bridges a [DeltaChat](https://delta.chat) email account to a HiveMind hub: a
HiveMind bridge is a satellite whose input and output are chat messages
instead of a microphone. Each incoming DeltaChat message becomes a
`recognizer_loop:utterance` bus message; the hub's `speak` reply is sent back
into the originating chat. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); the client
library is
[hivemind-bus-client](https://github.com/JarbasHiveMind/hivemind-bus-client).
Sibling bridges with the same shape (chat platform in, chat platform out):
`hivemind-telegram-bridge`, `HiveMind_mattermost_bridge` — check them for
prior art before inventing a new pattern here.

## Layout / build / test

- Package module: `hm_deltachat_bridge/`. Tests live in `tests/` (check
  before adding — do not create a second test directory). `tests/e2e/` drives
  the bridge against a real `hivemind-core` hub booted in-process by
  `hivescope`; only the DeltaChat transport is mocked there.
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests/test_bridge.py tests/test_smoke.py -q`.
  These use `AsyncFakeHiveMessageBus` for the HiveMind side and a stub bot for
  DeltaChat, so they run without a live hub or mailbox — treat them as a
  shape/wiring check, not a live-behaviour guarantee. `tests/e2e/` needs the
  `e2e` extra and is the one that actually exercises a real hub.
- `libdeltachat`/`deltachat-core` is a native dependency of the `deltachat`
  Python package; a missing system library breaks import, not just a test.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is
  a bug to FIX at the source, not to work around with a pin downgrade.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- **This bridge is async, not sync.** `HiveMindDeltaChatBridge` (in
  `hm_deltachat_bridge/__init__.py`) composes an
  `hivemind_bus_client.async_client.AsyncHiveMessageBusClient` — not the
  classic sync `HiveMessageBusClient`. Any borrowed pattern from a sync
  bridge (e.g. `hivemind-telegram-bridge`) needs translating: no
  `run_in_thread()`, no blocking `connect()`; the client runs on the
  application's own asyncio event loop.
- **Composition, not inheritance; connect once.** The client is built (or
  injected, for tests — see the `client=` constructor parameter and
  `AsyncFakeHiveMessageBus`) but not connected in `__init__`. The single
  `await self.client.connect(...)` call lives in `start()`, guarded by
  `self._started`, which also makes `start()`/`stop()` idempotent. Never add
  a second `connect()` call or duplicate the deltachat-thread bridging.
- **`connect()` must bound `handshake_max_retries`.** For the async client,
  bounded-handshake parity with the sync client landed via
  `hivemind-websocket-client` PR #201; the same unbounded-retry-forever
  default (`None`) applies — an unbounded `connect()` hangs indefinitely
  against a stalled or unreachable hub instead of failing fast. The current
  `await self.client.connect(site_id="deltachat")` call in `start()` does
  **not** pass `handshake_max_retries`. Treat that as a standing defect, not
  documented-as-fine behaviour: any change touching `start()`/`connect()`
  should add an explicit finite bound (exposed as a constructor/CLI
  parameter so operators can tune it), not leave it implicit.
- **The hub owns ACL, not this bridge.** A freshly registered HiveMind
  client is denied every message type until an admin runs `hivemind-core
  allow-msg recognizer_loop:utterance <client_id>` (and usually `speak`).
  This bridge has no way to grant itself permissions and must not try to
  work around a denial locally. `DeltaChatBot.allowed_emails` is a separate,
  bridge-side filter over which chat senders may originate traffic — it is
  not a substitute for hub-side message-type ACLs, and is not currently
  exposed as a CLI option (see the `TODO` in `__main__.py`).
- **Rejected credentials must fail fast.** A bounded `handshake_max_retries`
  is what turns "wrong access key/password" into a clean failure instead of
  a bridge that spins forever looking connected. Do not add retry/backoff
  logic on top of `connect()` that defeats this.
- **Forward upstream responses verbatim.** `_on_speak()` sends
  `message.data["utterance"]` to the deltachat chat unmodified; do not
  reformat, truncate, or add bridge-specific decoration to hub-authored
  text.
- **Two threads, one bridging seam.** `DeltaChatBot` runs the classic
  (callback-based, not asyncio-aware) `deltachat` library's blocking
  `account.wait_shutdown()` on its own daemon thread; `_on_delta_utterance`
  is the callback that thread invokes. It schedules the HiveMind emit onto
  the bridge's asyncio loop with `asyncio.run_coroutine_threadsafe` — never
  `await` directly from that callback, and never call asyncio-loop-bound
  client methods from the deltachat thread any other way. `_on_speak` runs
  on the receive task already on the loop and calls `bot.speak()`
  (`chat.send_text`) synchronously; that call is treated as safe to make
  inline because the deltachat library is thread-safe for it — do not
  offload it to a thread pool without a reason to revisit that assumption.
